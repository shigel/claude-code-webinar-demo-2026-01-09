# Subagents 検証結果分析

## 概要

「不具合を修正して」というシンプルなプロンプトで、3つのモジュール（calculator, advanced, formatter）のバグ修正を実行。Subagents の有無による違いを比較。

---

## 結果サマリー

### With Subagents（並列実行）

| モデル | 実行時間 | 並列実行 | Worktree | 結果 |
|--------|----------|----------|----------|------|
| Opus 4.5 | 1m 17s | ✅ 3 agents (~10k tokens each) | ✅ 3 branches | 成功・個別コミット |
| Sonnet 4.5 | 1m 36s | ✅ 3 agents (~10k tokens each) | ✅ 3 branches | 成功・個別コミット |
| Haiku 4.5 | 1m 36s | ⚠️ 権限エラーで直接修正にフォールバック | ⚠️ | 成功 |

### Without Subagents（順次実行）

| モデル | 実行時間 | 並列実行 | Worktree | 結果 |
|--------|----------|----------|----------|------|
| Opus 4.5 | 53s | ❌ | ❌ 直接編集 | 成功 |
| Sonnet 4.5 | 1m 16s | ❌ | ❌ 直接編集 | 成功 |
| Haiku 4.5 | 42s | ❌ | ❌ 直接編集 | 成功 |

---

## 観察結果

### 1. 実行時間

| 比較 | With Subagents | Without Subagents | 差分 |
|------|----------------|-------------------|------|
| Opus | 1m 17s | 53s | +24s (45%増) |
| Sonnet | 1m 36s | 1m 16s | +20s (26%増) |
| Haiku | 1m 36s* | 42s | +54s (129%増) |

\* Haiku は Subagent で権限エラーが発生し、直接修正にフォールバック

**結論**: このタスクでは Subagents を使った方が遅い。理由:
- Worktree セットアップのオーバーヘッド（約10秒）
- 各 Subagent の起動コスト
- コンテキスト準備時間

### 2. 動作の違い

#### With Subagents
```
1. テスト実行 → 失敗を検出
2. CLAUDE.md の指示を読み取り
3. 各モジュールに worktree 作成（3つ）
4. test-runner を並列起動（3つ同時）
5. 各 worktree で独立して修正・テスト・コミット
6. 結果報告
```

#### Without Subagents
```
1. テスト実行 → 失敗を検出
2. ソースファイルを読み込み
3. 3つのファイルを順次修正
4. テスト再実行で確認
5. 結果報告
```

### 3. Subagents の価値が発揮された点

| 価値 | 説明 |
|------|------|
| ✅ 並列処理 | 3つのエージェントが同時に作業 |
| ✅ ブランチ分離 | 各モジュールが独立したブランチで修正 |
| ✅ 独立コミット | 「fix: calculator」「fix: advanced」「fix: formatter」の3コミット |
| ✅ 失敗の隔離 | 1つが失敗しても他に影響しない |
| ✅ コンテキスト分離 | 各エージェントが自分のタスクに集中 |

### 4. Subagents の価値が発揮されなかった点

| 課題 | 説明 |
|------|------|
| ⚠️ セットアップコスト | Worktree 作成に時間がかかる |
| ⚠️ 単純タスク | この修正は1行変更×3ファイル。順次でも十分 |
| ⚠️ Haiku の問題 | 権限エラーでフォールバック |
| ⚠️ 総時間 | 結果的に Without より遅い |

## Subagents が真価を発揮するケース

### 向いているケース

1. **大規模・独立タスク**: 各モジュールの修正が複雑（10ファイル以上）
2. **レビュー重視**: 各変更を個別ブランチで PR レビューしたい
3. **リスク分散**: 1つの修正失敗が全体に波及しないようにしたい
4. **並列性が効く**: 各タスクに10分以上かかる場合、時間短縮効果が大きい

### 向いていないケース

1. **単純な修正**: 1行変更が数個程度
2. **スピード優先**: オーバーヘッドが許容できない
3. **同一ファイル修正**: 複数エージェントが同じファイルを触るとコンフリクト

---

## ウェビナーでの補足ポイント

1. **「並列」の見え方**
   - ログでは `3 test-runner agents finished` が同時に完了
   - 順次なら約3分のところ、約1分半で完了（相対的な短縮）

2. **コード品質**
   - 各ブランチで独立テスト → 修正の信頼性向上
   - マージ時にレビュー可能

3. **スケーラビリティ**
   - 10モジュールなら効果が顕著（順次30分 vs 並列5分）
   - 実プロジェクトでは価値が高まる

4. **今回のデモの位置づけ**
   - 「Subagents が動く」ことの確認
   - 実際の価値は大規模タスクで発揮される

---

## 結論

このデモでは Subagents の「機能的な動作」は確認できたが、「時間短縮」という価値は示せなかった。

**理由**: タスクが単純すぎた（1行修正×3ファイル）

**教訓**: Subagents の真価は「複雑で独立した並列タスク」で発揮される。デモでその価値を示すには、より複雑なシナリオが必要。

### 推奨

ウェビナーでは以下を強調:
- 「並列で動いている」という見た目のインパクト
- 「ブランチ分離」による品質管理
- 「大規模プロジェクトでの時間短縮」という将来的な価値
